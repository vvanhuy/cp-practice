Mọi thông báo lỗi trong tài liệu này được lấy nguyên văn bằng cách compile và chạy thật với g++ 15 trên Ubuntu. Phiên bản g++ khác có thể diễn đạt hơi khác, nhưng cấu trúc và ý nghĩa giữ nguyên.

1. Bản đồ các loại lỗi

Mọi chương trình đi qua 3 cửa: compile → chạy → so kết quả. Lỗi ở cửa nào thì có cách tìm riêng.

Viết code ──▶ [ COMPILE ] ──✗──▶ CE Lỗi cú pháp: không tạo được chương trình │ ├──⚠──▶ WARNING Vẫn chạy, nhưng gần như chắc chắn có bug ▼ [ CHẠY ] ──✗──▶ RE Crash: tràn mảng, chia 0, con trỏ sai... │ ──∞──▶ TLE Treo hoặc chạy quá chậm ▼ [ SO OUTPUT ] ──✗──▶ WA Chạy xong nhưng in sai

Càng xuống dưới càng khó tìm. Với CE, compiler chỉ thẳng số dòng. Với WA, không ai chỉ cho bạn — phải tự đi tìm. Vì vậy mục tiêu là đẩy lỗi lên càng cao càng tốt: bật warning để bắt bug ngay lúc compile, bật sanitizer để biến "sai âm thầm" thành "crash có chỉ dòng".

2. Lỗi compile (CE)

2.1. Giải phẫu một dòng lỗi

sol.cpp:9:5: error: expected initializer before ‘cin’
└──┬──┘ │ │  └─┬──┘ └────────────── nội dung ──────────────┘
  file dòng cột loại
  • file:dòng:cột — vị trí. Trong terminal VS Code, giữ Ctrl và click vào đó để nhảy thẳng tới dòng lỗi.
  • loại — error (phải sửa mới compile được), warning (vẫn compile được nhưng nên sửa), note (giải thích thêm cho dòng phía trên, đọc kèm).
  • nội dung — compiler mô tả điều nó mong đợi mà không thấy. Từ khóa hay gặp: expected (đang chờ), declared (khai báo), scope (phạm vi), conversion (chuyển kiểu), operand (toán hạng).

2.2. Ba quy tắc vàng

① Chỉ đọc lỗi ĐẦU TIÊN Một lỗi (ví dụ thiếu }) có thể sinh ra hàng chục lỗi "dây chuyền" phía sau. Sửa lỗi đầu tiên → compile lại → đọc lỗi đầu tiên mới. Lặp lại.
② Lỗi thật thường nằm ở dòng được báo, HOẶC NGAY TRƯỚC NÓ Compiler chỉ phát hiện ra thiếu ; khi đọc sang dòng kế tiếp. Nếu dòng được báo trông hoàn toàn đúng → nhìn lên dòng trên.
③ Lỗi dài toàn chữ std::__cxx11::basic_... và hàng chục dòng note: candidate? Đó là lỗi liên quan thư viện chuẩn (template). Bỏ qua phần dài dòng, chỉ đọc dòng error: đầu tiên có tên file của bạn và tìm cụm operand types are ‘A’ and ‘B’ — nó cho biết bạn đang dùng toán tử với hai kiểu dữ liệu không hợp nhau.

3. Warning — lỗi ngầm compiler đã báo trước

Warning không chặn compile, nên người mới hay bỏ qua. Nhưng trong code thi đấu, gần như mọi warning đều là bug. Quy tắc: compile phải sạch — 0 warning (thanh trạng thái VS Code hiện ⊗ 0 ⚠ 0).

Warning (g++ 15)Code gây raVì sao là bug → sửa
suggest parentheses around assignment used as truth value [-Wparentheses]if (x = 0)= là gán, không phải so sánh. Điều kiện luôn sai và x bị đổi thành 0. Sửa: ==
‘cnt’ may be used uninitialized [-Wmaybe-uninitialized]int cnt; cnt++;Biến cục bộ chưa gán chứa giá trị rác. Trên máy có thể ra đúng, lên judge ra sai. Sửa: int cnt = 0;
statement has no effect [-Wunused-value]n / 10;Tính xong rồi vứt đi. Sửa: n /= 10; hoặc n = n / 10;
suggest braces around empty body in an ‘if’ statement [-Wempty-body]if (x == 2); cout << x;Dấu ; ngay sau if làm thân if rỗng — dòng tiếp theo luôn chạy. Xóa ;
control reaches end of non-void function [-Wreturn-type]Hàm int có nhánh không returnKết quả trả về là rác, có thể crash. Thêm return cho mọi nhánh
comparison of integer expressions of different signedness: ‘int’ and ‘...size_type’ [-Wsign-compare]for (int i = 0; i < v.size(); i++)Thường vô hại, nhưng v.size() - 1 khi vector rỗng ra số khổng lồ (không âm được). Sửa: i < (int)v.size()

Mẹo: biến warning thành error Thêm cờ -Werror vào lệnh compile, khi đó mọi warning đều chặn compile như error — buộc bạn phải sửa. Hữu ích trong giai đoạn mới học để tập thói quen.

4. Lỗi khi chạy (RE) — đọc báo cáo sanitizer

Vì sao phải có sanitizer? Mình đã chạy thử chương trình ghi vào a[5] của một vector 5 phần tử: không có sanitizer → chạy bình thường, exit code 0, không báo gì. Lỗi vẫn ở đó — nó âm thầm ghi đè lên vùng nhớ khác, và lên judge sẽ ra WA hoặc RE một cách "khó hiểu". Sanitizer biến lỗi âm thầm thành lỗi có chỉ số dòng.

4.1. Đọc báo cáo AddressSanitizer (ASan)

==22221==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x6d87...
  └─ ① LOẠI LỖI
WRITE of size 4 at 0x6d8747be0054 thread T0
  └─ ② ghi (WRITE) hay đọc (READ)
    #0 0x60aa7b8b058f in main /home/huy/.../sol.cpp:3
  └─ ③ DÒNG LỖI: dòng #0 (#1, #2...) đầu tiên có file của bạn
    #1 0x7540b6a2a600 in __libc_start_call_main ...
  └─ bỏ qua: code hệ thống
... địa chỉ bộ nhớ, Shadow bytes, legend — bỏ qua hết ...
SUMMARY: AddressSanitizer: heap-buffer-overflow .../sol.cpp:3 in main
  └─ tóm tắt: loại lỗi + dòng

Chỉ cần 3 thứ: ① loại lỗi ở dòng ERROR:; ② READ hay WRITE; ③ dòng #0 (hoặc #1, #2...) đầu tiên có tên file của bạn. Nếu lỗi xảy ra trong hàm bạn tự viết, stack trace cho thấy cả chuỗi gọi: #0 in f(int) sol.cpp:5 ← #1 in main sol.cpp:12.

4.2. Đọc báo cáo UndefinedBehaviorSanitizer (UBSan)

overflow.cpp:3:59: runtime error: signed integer overflow: 2000000000 + 2000000000 cannot be represented in type 'int'
⚠️ UBSan chỉ báo, KHÔNG dừng chương trình Chương trình chạy tiếp với kết quả sai và exit code vẫn là 0 → run.sh sẽ báo ❌ WA chứ không phải 💥 RE. Vì vậy mỗi khi WA, hãy kéo terminal lên xem có dòng runtime error: nào không.

5. Sai kết quả (WA) — danh sách kiểm tra

WA là lỗi khó nhất vì không ai chỉ dòng cho bạn. Trước khi mở debugger, đi qua danh sách này — 80% lỗi WA nằm ở đây.

5.1. Mười lỗi WA kinh điển

#LỗiDấu hiệu và cách kiểm tra
1Tràn sốĐề cho số tới 109, 231, 232... mà dùng int (tối đa ≈ 2,1×109). Tổng/tích của nhiều số rất dễ vượt. → long long (≈ 9,2×1018). Nhìn terminal tìm signed integer overflow
2Quên reset biến giữa các testĐề có nhiều test (while (cin >> n)) mà biến đếm/tổng/mảng khai báo ngoài vòng lặp → test 2 cộng dồn kết quả test 1. Test đầu đúng, test sau sai là dấu hiệu rõ nhất. → Khai báo biến bên trong vòng lặp
3Sai định dạng outputThiếu/thừa dấu cách, dòng trống giữa các test, viết hoa/thường, Case #1: thiếu dấu cách... Đọc lại phần Output của đề từng chữ. Dùng diff của run.sh
4Trường hợp biênn = 0, n = 1, số âm, số lớn nhất, chuỗi rỗng, tất cả phần tử bằng nhau, input đảo thứ tự. Sample của đề thường không có những test này — phải tự thêm
5Khởi tạo max/min saiint mx = 0 sai khi dãy toàn số âm. → mx = a[0] hoặc mx = INT_MIN / LLONG_MIN
6Chia nguyêndouble avg = sum / n; với sum, n là int → phép chia nguyên chạy trước rồi mới đổi sang double. → (double)sum / n
7Số thựcLàm tròn sai số chữ số (fixed << setprecision(2)); so sánh a == b với double → dùng fabs(a - b) < 1e-9; in ra -0.00
8Trộn cin >> với getlineSau cin >> n, ký tự xuống dòng vẫn còn trong bộ đệm → getline đầu tiên đọc ra chuỗi rỗng. → Thêm cin.ignore(); trước getline, hoặc dùng getline cho mọi thứ
9Đọc sai kiểu inputĐề đọc đến EOF mà code chỉ đọc 1 test; đề có số test T mà code đọc đến EOF; đề kết thúc bằng 0 0 mà code không dừng
10Hiểu sai đềĐọc lại đề, tự giải tay sample. Nếu ra khác đáp án mẫu → bạn hiểu sai đề, chưa phải lỗi code

5.2. Dùng diff của run.sh

❌ WA - khác ở:
--- của bạn
+++ đáp án
@@ -1,3 +1,3 @@        ← vùng khác nhau: từ dòng 1, dài 3 dòng
 2                      ← dòng bắt đầu bằng dấu cách: giống nhau
--2                     ← dấu "-" là của BẠN: in ra "-2"
+2                      ← dấu "+" là ĐÁP ÁN: phải là "2"
 100

Ở ví dụ này test 2 sai: bạn in -2, đáp án là 2 → nghi ngay "thứ tự hai số bị đảo" (lỗi #4) hoặc "quên lấy trị tuyệt đối".

5.3. Khi sample đúng mà nộp vẫn WA

  1. Tự viết thêm test biên (mục 5.1 #4) và tính tay đáp án.
  2. Vào uDebug (nút trên trang bài của vjudge hoặc udebug.com): cộng đồng đăng sẵn input khó và đáp án đúng cho bài UVa. Copy input vào in.txt, đáp án vào out.txt, chạy run.sh.
  3. Kiểm tra lại giới hạn trong đề → có cần long long không.
  4. Kiểm tra định dạng: dòng trống cuối, dấu cách cuối dòng (một số judge khắt khe).

6. Quá thời gian (TLE) và chương trình bị treo

6.2. Chương trình bị treo

  1. Bấm Ctrl+C trong terminal để dừng.
  2. Có phải đang chờ input không? Nếu chạy không kèm in.txt, chương trình đang đợi bạn gõ. run.sh báo "(Không có in.txt → nhập tay...)" nếu thiếu file.
  3. Đọc warning: statement has no effect (ví dụ n / 10;) là thủ phạm kinh điển.
  4. Dùng debugger: chạy F5, đợi vài giây, bấm nút Pause (‖) trên thanh debug → VS Code dừng ngay dòng đang lặp. Xem biến điều khiển vòng lặp có thay đổi qua mỗi vòng không.
Câu hỏi kiểm tra mọi vòng while "Biến trong điều kiện có thay đổi bên trong vòng lặp không, và có tiến dần tới điều kiện dừng không?" Ví dụ while (n != 0) mà bên trong không có lệnh nào làm n thay đổi → chắc chắn vô hạn.

6.4. TLE do nhập/xuất chậm

  • Luôn có ios::sync_with_stdio(false); cin.tie(nullptr); (đã có trong template).
  • Dùng '\n' thay vì endl. endl ép đẩy bộ đệm ra màn hình mỗi lần → chậm khi in nhiều dòng.
  • Không trộn cin/cout với scanf/printf sau khi đã tắt đồng bộ.

7. Debugger trong VS Code

Debugger cho phép dừng chương trình ở bất kỳ dòng nào và xem giá trị mọi biến tại thời điểm đó. Đây là công cụ chính để tìm lỗi WA, và cũng là cách tốt nhất để hiểu đệ quy, con trỏ, vòng lặp lồng nhau khi học LT1/LT2.

7.1. Bắt đầu một phiên debug

  1. Mở file sol.cpp cần debug (có in.txt cùng thư mục).
  2. Click vào lề trái số dòng → hiện chấm đỏ (breakpoint).
  3. Thanh bên trái → icon Run and Debug (▷ có con bọ) → dropdown trên cùng chọn "Debug (đọc in.txt)". VS Code nhớ lựa chọn này cho lần sau.
  4. Bấm F5. VS Code tự compile (bản debug, có sanitizer) rồi chạy, dừng ở breakpoint.
Hai cấu hình đã có trong .vscode/launch.json Debug (đọc in.txt) — input lấy từ in.txt cùng thư mục. Dùng 95% thời gian.
Debug (nhập tay) — gõ input vào tab Terminal. Dùng khi muốn thử nhanh một input nhỏ.

7.6. Debug Console

Khi đang dừng, gõ biểu thức vào ô dưới cùng của tab Debug Console rồi Enter để tính ngay, ví dụ a + b, v.size(). Gõ lệnh gdb trực tiếp bằng tiền tố -exec: -exec p v (in biến), -exec info locals (in mọi biến cục bộ).

7.7. Ba tình huống debug điển hình

a) Vòng lặp tính sai

Breakpoint ở dòng đầu thân vòng lặp → thêm vào WATCH các biến quan trọng (i, sum, mx) → F5 từng vòng, so với bảng tính tay. Vòng đầu tiên lệch → lỗi ở đó.

b) Đệ quy sai

Breakpoint ở dòng đầu hàm đệ quy → F5 nhiều lần, nhìn CALL STACK dài ra (đi xuống) rồi ngắn lại (quay lên). Kiểm tra: có đi đến trường hợp cơ sở không? Giá trị trả về ở mỗi tầng có đúng không? Dùng Shift+F11 để xem một tầng trả về gì.

c) Chương trình bị treo

F5 (không cần breakpoint) → đợi 2–3 giây → bấm ‖ Pause → dòng tô vàng là chỗ đang lặp. Xem biến điều khiển vòng lặp; F10 vài lần xem nó có đổi không.

Lưu ý: output hiện ra trễ khi debug Template dùng sync_with_stdio(false) và '\n' nên cout gom output vào bộ đệm, chưa in ngay. Khi debug, đừng dựa vào terminal để xem kết quả — nhìn vào VARIABLES/WATCH. Nếu cần thấy ngay thì in bằng cerr (không có bộ đệm).
Khi debug không dừng ở breakpoint ① Kiểm tra đã chọn đúng cấu hình "Debug (đọc in.txt)" chưa; ② chương trình có thể kết thúc trước khi tới dòng đó (ví dụ in.txt rỗng, vòng lặp không chạy lần nào); ③ breakpoint màu xám rỗng = dòng không có code thực thi (dòng trống, dòng chỉ có {) — đặt ở dòng khác.

8. Debug không cần debugger

Đôi khi in ra màn hình nhanh hơn mở debugger, đặc biệt lúc thi (môi trường thi có thể không có debugger quen thuộc).

8.1. In ra cerr trong khối #ifdef LOCAL

#ifdef LOCAL
cerr << "i = " << i << ", sum = " << sum << '\n';
#endif
  • cerr in ra luồng lỗi: không bị gom bộ đệm, và run.sh không đem nó đi so với đáp án.
  • #ifdef LOCAL: chỉ chạy trên máy bạn (đã có cờ -DLOCAL). Lỡ quên xóa khi nộp bài cũng không bị WA.
  • Gõ nhanh bằng snippet dbg + Tab.

8.2. In cả vector

#ifdef LOCAL
for (int x : v) cerr << x << ' ';
cerr << '\n';
#endif

8.3. assert — tự kiểm tra giả định

assert(n >= 1 && n <= 100000);   // nếu sai: dừng ngay, báo dòng và điều kiện
assert(lo <= hi);

Khi điều kiện sai, chương trình dừng với thông báo Assertion `lo <= hi' failed kèm số dòng (exit code 134). Dùng để kiểm tra những điều bạn tin là luôn đúng — nếu niềm tin sai, bạn biết ngay chỗ nào.

8.4. Giảm input — chia đôi để tìm test sai

Khi in.txt có nhiều test và kết quả sai: xóa bớt một nửa số test → còn sai không? Tiếp tục chia đôi cho đến khi còn một test nhỏ nhất vẫn sai. Debug trên test đó sẽ nhanh hơn rất nhiều.

11. Bảng tra nhanh

Gặp lỗi compile

  • Chỉ đọc lỗi đầu tiên, sửa, compile lại
  • Dòng báo lỗi trông đúng → nhìn dòng trên
  • expected ‘;’ / expected initializer → thiếu ;
  • not declared in this scope → sai tên / sai phạm vi
  • expected ‘}’ at end of input → thiếu }
  • no match for ‘operator<<’ → không in thẳng vector/struct
  • undefined reference → thiếu main / thiếu thân hàm

Warning nguy hiểm nhất

  • -Wparentheses → = thay vì ==
  • -Wmaybe-uninitialized → biến chưa gán
  • -Wunused-value → n / 10; quên gán
  • -Wempty-body → if (...);
  • -Wreturn-type → hàm thiếu return

Gặp RE — tìm file.cpp:DÒNG

  • *-buffer-overflow → ngoài mảng/vector
  • stack-overflow → đệ quy vô hạn / mảng cục bộ quá lớn
  • division by zero / exit 136 → chia 0
  • SEGV ... 0x000000000000 → con trỏ null
  • exit 139 → Segmentation fault

Gặp WA — kiểm tra theo thứ tự

  1. Terminal có runtime error:? → tràn số → long long
  2. Test đầu đúng, test sau sai? → quên reset biến
  3. Định dạng: dấu cách, dòng trống, Case #
  4. Biên: 0, 1, âm, lớn nhất, đảo thứ tự
  5. mx = 0 với số âm
  6. Chia nguyên: (double)sum / n
  7. cin >> rồi getline → cin.ignore()
  8. uDebug lấy test khó
  9. Thu nhỏ input → tính tay → F5

Bị treo / TLE

  • Ctrl+C để dừng
  • Thiếu in.txt → đang chờ nhập
  • F5 → ‖ Pause → xem dòng tô vàng
  • ~108 phép tính / giây
  • '\n' thay endl
